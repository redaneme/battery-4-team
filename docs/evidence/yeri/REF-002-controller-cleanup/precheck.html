이유

  • 7건 모두 화면·API·계산 결과를 바꾸지 않는 정리다(세션 사용자 꺼내기, toForm 이동, 모델 설정 묶기, @RestController, 변수명, 주석, 문서 이름). PRD 10장 범위 밖 저촉과 요구 변경이 없다.
  • JUnit 기준선 22건 통과(build/test-results 확인). E2E 기준선은 같은 커밋 3ab240a 에서 REF-002 점검이 별도 포트·메모리 DB 로 돌린 45건 통과(test.fail() 3건 포함) 기록을 인용했다. 이번 점검에서 재실행은 하지 않았다.
  • 큰 변경·높은 위험 없음: 변경 파일 약 7~8개, DB·엔티티·핵심 불변식 코드 변경 없음(OrderService 는 주석만).
  • 요청 6번 확인: 읽기 전용 트랜잭션은 SimulationService 가 아니라 그 아래 MasterService.currentMaster 에 있다(SimulationService 에는 @Transactional 없음). 결론(결과 같음, 주의 필요)은 맞아 코드 변경 없이 OrderService.confirm 주석으로 남긴다.

배경 · 사용자가 어떤 상황인가 이해함

직전 리팩토링(역할별 파일 분리, 커밋 93195ea) 뒤 코드 리뷰에서 나온 잔여 정리 7건이다. 세션 사용자 꺼내기와 모델 설정이 반복되고, 마스터 폼 변환이 컨트롤러에 남아 있고, 이름·애노테이션·문서 인용이 옛 모습이다.

근거

OrderController.java 와 ApiController.java 의 같은 세션 캐스팅, MasterController 의 toForm(routeKey, WON_PER_EOK 직접 사용)과 factories/countries 두 곳 반복, ApiController 의 @Controller + @ResponseBody, DataInitializer 의 service 필드, INTENT.md:38 의 BatteryService.confirm(실제 OrderService.confirm).

목적 · 왜 필요한가 이해함

동작은 그대로 두고 중복을 한 곳으로 모으고, 서비스 규칙을 서비스에 두어 책임을 분명히 하고, 이름과 문서를 현재 코드와 맞춘다.

근거

요청 7개 항목 문구(@SessionAttribute 로 한 곳에, 서비스 쪽으로, 메서드로 묶기, @RestController, 변수명, 트랜잭션 주의, 문서 이름 정정). INTENT 8.5 는 구조 정리를 허용하는 방향.

위험심각도대응
@SessionAttribute 는 기본 required=true 라 세션 값이 없으면 null 이 아니라 400 으로 실패한다.낮음LoginInterceptor(WebConfig 에서 /** 적용, /login 등 제외)가 앞에서 막아 이 두 경로에서는 세션 사용자가 항상 있다(코드 확인). 미로그인 302/401 은 기존 JUnit·E2E 가 지킨다.
toForm 을 옮기면서 억 원 환산(stripTrailingZeros)이나 입력칸 이름 규칙이 달라질 수 있다.낮음본문을 그대로 옮기고 값을 직접 단언하는 JUnit 1건을 둔다. E2E readMasterForm(E2E-036~040)이 화면 값을 확인한다.
모델 설정 묶음을 @ModelAttribute 메서드로 만들면 redirect:/master 응답에도 모델이 쓰일 수 있다.낮음private 메서드로 묶어 두 곳에서 호출한다(현재 동작과 같음).
@RestController 전환 후 이 클래스에 뷰 이름을 돌려주는 메서드를 두면 JSON 으로 나간다.낮음현재 3개 메서드 모두 이미 @ResponseBody 이므로 직렬화 동일. 뷰 반환 메서드는 두지 않는다.
