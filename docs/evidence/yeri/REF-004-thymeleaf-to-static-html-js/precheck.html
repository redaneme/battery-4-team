1판단

리팩토링으로 진행 가능(GO): 기준선(JUnit 23건, E2E 45건)을 직접 확인했고 사용자 결정 5건이 모두 들어왔으며 큰 변경임을 사용자가 알고 있다.

이유

  • 버그가 아니라 리팩토링 요청이다. 화면 기술 교체이고 사용자에게 보이는 동작 유지가 조건이다. (INTENT 8.5: 화면 기술은 바꿔도 된다)
  • 직전 점검의 질문 5건(테스트 헬퍼 수정 허용, 결함 3건 처리, 전체 E2E 설정, 문서 수정, 화면 주소 유지)에 사용자가 모두 답했다.
  • 기준선을 직접 확인했다. ./gradlew cleanTest test 는 23건 전부 통과, 별도 포트 8093·메모리 DB 의 E2E 전체는 45건이 모두 기대한 결과(42건 통과 + test.fail() 3건 예상 실패)였다. 개발 서버(8080)와 개발 DB 는 쓰지 않았다.
  • 큰 변경이지만 사용자가 요청에서 알고 있다고 밝혔다. DB·엔티티·핵심 업무 규칙 코드는 바꾸지 않는다.
  • 문서 충돌 없음. INTENT 5.7 과 6장은 이 결정으로 달라지므로 문서를 먼저 고친다(INTENT 8.1, 사용자가 허용).

⚠ 경고

  • 큰 변경: 계층 전부, 대략 25~30개 파일. 사용자가 알고 있어 기록만 한다.
  • 인증 경로: 정적 HTML 도 비로그인이면 /login 으로 가야 한다. forward 가 인터셉터를 다시 거치는지 확인하지 못했다.
  • 비동기 렌더링: 화면이 fetch 뒤에 그려져, 기다리지 않고 바로 읽는 E2E 헬퍼가 간헐 실패할 수 있다.
  • 결함 보존: 취소 직후 오류 화면과 없는 주문 번호의 500 화면을 일부러 그대로 둔다. 고치지 않는다.

배경 · 사용자가 어떤 상황인가 이해함

서버가 템플릿 6개로 목록·상세·마스터 값·로그인 사용자명·안내 문구를 그리고, 로그인·마스터 저장·상태 변경은 폼 POST 와 302 이동으로 처리한다. 주문 추가 화면만 이미 JSON API 를 쓴다. 이 렌더링을 정적 HTML 과 JS 가 API 로 받아 그리게 바꾸려는 상황이다.

근거

요청 문구, templates/*.html, AuthController·OrderController·MasterController·GlobalModelAttributes, LoginInterceptor, static/js/order-new.js

목적 · 왜 필요한가 이해함

화면 구조를 정적 파일(프런트)과 JSON API(백엔드)로 나누되 사용자가 보는 화면·흐름·문구·주소는 같아야 한다. 끝나면 서버에 Thymeleaf 가 없고 E2E 가 기준선과 같은 결과(42건 통과 + 알려진 결함 3건 예상 실패)다.

근거

요청 문구와 사용자 결정 (1)~(5), INTENT 8.5(화면 기술은 바꿔도 된다)

3규모와 위험

변경 규모 (여러 계층, 많은 파일, DB 변경, 핵심 규칙 변경, 되돌리기 어려움 → 큼)

작음중간큼

사용자가 이 규모·위험을 알고 있는가: 예 — "여러 계층에 걸친 큰 변경임을 알고 있어" 와 결정 5건을 요청에 적었다.

위험심각도대응
동시 변경 보호(원칙 5): 상태 변경에 화면에서 본 version 을 서버가 계속 받아야 한다높음상세 API 응답의 version 을 JS 가 보관해 보낸다. 충돌 문구는 서버가 만든다. E2E-034 로 확인하고 오류 뒤에는 새로 읽은 상태를 보여 준다.
인증 경로(원칙 14): 정적 HTML 이 인터셉터를 우회할 수 있다. 제외 경로에 /login.html, /api/login 이 새로 필요하다높음그 둘만 제외하고 나머지는 막는다. 비로그인 302 와 /api 401 을 E2E-003·004 와 JUnit 단언으로 확인한다.
뒤로 가기(E2E-005): 정적 페이지가 캐시되어 로그아웃 뒤에도 보일 수 있다중간화면 응답에 Cache-Control: no-store, 각 페이지 JS 가 첫 API 가 401 이면 /login 으로 이동.
즉시 읽는 헬퍼의 간헐 실패(예: e2e-028 이 goto 직후 이력 행 수 1을 기대)중간헬퍼에 화면이 그려질 때까지 기다리는 단계를 넣는다(단언 의도는 그대로). 연속 2회 실행으로 확인.
취소 뒤 이동 경쟁: 예전엔 서버 302 가 응답에 들어 있었으나 이제 JS 가 응답을 받은 뒤 이동한다. E2E-032 가 바로 /orders 로 goto 하면 겹칠 수 있다중간응답 처리 직후 동기적으로 이동한다. 반복 실행으로 확인한다.
마스터 저장(원칙 7): 전부 아니면 전무, 오류 목록, 오류 시 입력값 유지, 성공 뒤 안내와 값 다시 읽기를 JS 가 재현중간서버 검증(updateMaster)은 그대로. form[action="/master"] 와 input name 유지(E2E-040 이 noValidate 를 켠다).
서버 포맷 차이: 날짜 yyyy-MM-dd HH:mm, 천 단위 쉼표, 억원 소수 2자리중간서버가 이미 포맷한 문자열을 API 로 보내 차이를 없앤다.
로그인 실패를 401 로 주면 공통 처리가 /login 이동으로 오해해 문구가 안 보인다낮음로그인 실패는 400 + error 문구로 주고 login.js 가 직접 처리한다.

가정 (확인하지 못한 것)

  • Spring Boot 4.1.1 에서 Thymeleaf 를 빼도 /error 기본 화면(Whitelabel)이 지금과 같게 나오는지: 확인하지 못함. 구현 뒤 E2E-033·035 가 계속 예상 실패인지로 확인한다.
  • forward 요청이 인터셉터를 다시 거치는지: 확인하지 못함. 구현 때 확인한다.
  • Playwright 의 Chrome 에서 뒤로 가기 캐시 동작: 확인하지 못함. E2E-005 실행으로 확인한다.
  • docs/understand/* 안내서가 화면 구조를 설명하는지: grep 에서 Thymeleaf·templates 언급은 안 나왔고 내용은 확인하지 못함.

알려진 결함 테스트 (test.fail())에 미치는 영향

의도적으로 보존한다. E2E-033(취소 직후 이동)은 취소 뒤 /orders/{id} 로 이동하는 현재 동작을, E2E-035(없는 주문 번호)는 존재 확인 뒤 예외를 그대로 던져 HTTP 500 기본 오류 화면이 나오는 현재 동작을, E2E-013b 는 Planner 를 건드리지 않아 그대로 실패한다. 구현 후에도 세 건이 계속 예상 실패여야 한다. 결함 수정은 별도 버그수정 Loop.
