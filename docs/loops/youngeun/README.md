# 영은의 Loop 설계 (`/ih` · Implement Harness)

battery 프로그램에 **구현 요청**을 처리하는 Loop입니다. Dynamic Workflow로 만들었고, `/ih <구현할 내용>`으로 실행합니다.
이 문서는 설계를 설명합니다.

## 1. 한 줄 설명

요청을 받으면 **먼저 점검**(prepare)하고, 문제가 없으면 **구현**(implement)한 뒤, **검증**(verify)합니다. 검증에 실패하면 **그 문제를 들고 점검 단계로 되돌아가** 다시 시도하고, 통과하면 보고서를 남기고 끝납니다.

## 2. 흐름

```
 /ih <구현할 내용>
  ▼
┌─► [prepare]   배경·목적 / 문서 규칙 / 규모·위험 점검 ──► precheck.html
│     │         체크리스트 3개 작성
│     ├─ HILP ──► ★ 루프 종료 (사람에게 질문·경고를 돌려줌)
│     ▼ GO
│   [implement] Plan → 구현 → 자가검증
│     ▼
│   [verify]    체크리스트·테스트·Lint·문서 규칙 확인
│     ├─ PASS ──► report.html 작성 ──► ★ 루프 종료
│     ▼ FAIL
└─────┘  실패 내용을 들고 prepare로 되돌아감 (최대 3라운드)
```

## 3. 단계별로 하는 일

### prepare (구현 전 점검)
코드는 건드리지 않고 점검만 합니다. 다음을 확인합니다.

1. **배경 이해** — 사용자가 어떤 상황인지 이해했는가
2. **목적 이해** — 이 기능이 왜 필요한지 이해했는가
3. **문서 규칙 부합** — 요청이 `PRD.md`, `INTENT.md`의 규칙과 어긋나지 않는가
4. **규모와 위험** — 변경이 너무 거대하거나 심각한 위험이 있는데 사용자가 모르고 있지 않은가

하나라도 걸리면 추측으로 채우지 않고 `HILP`를 반환합니다. 문제가 없으면 `GO`와 함께 **구현 후 확인할 체크리스트 3개**와 구현 방향(brief)을 반환합니다. 요청의 Loop 종류(`integrate | develop | refactor | bugfix`)도 정해 템플릿의 `data-loop`에 씁니다.

### implement (구현)
코드를 수정하기 전에 **Plan**(목적, 관련 코드, 수정할 파일, 가정)을 세우고, 범위 안에서만 구현합니다. 끝나면 **자가검증**(Plan 대조, 빌드·테스트 실행, `git diff` 확인)을 하고 결과를 보고합니다.

### verify (검증)
implement의 자가검증을 믿지 않고 직접 확인합니다.

1. prepare의 **체크리스트 3개**를 항목별로 확인
2. 관련 **테스트 실행** (Gradle, Playwright). 실행하지 못한 테스트는 통과로 치지 않음
3. **Lint** 실행. 오류가 있으면 FAIL
4. **문서 규칙 부합** 확인 (`PRD.md`, `INTENT.md`)

하나라도 어긋나면 FAIL, 모두 충족하면 PASS입니다.

## 4. 피드백 루프와 종료 조건

| 상황 | 동작 |
|---|---|
| verify **FAIL** | `issues`(어느 항목이 왜 실패했는지)와 직전 구현 요약을 들고 **prepare로 되돌아감**. prepare가 그 문제를 해결하기 위해 점검·체크리스트·brief를 다시 만듦 |
| verify **PASS** | `report.html` 작성 후 **루프 종료** |
| prepare **HILP** | **루프 종료**. 사람이 답하거나 결정해야 다시 시작할 수 있음 |
| **3라운드** 안에 통과 못 함 | 조용히 넘어가지 않고 `failed`와 남은 문제를 결과에 명시하고 종료 |
| 단계가 중단됨 | `aborted`와 중단된 단계를 반환 |

## 5. Human-in-the-loop

사람이 끼어드는 지점은 **prepare가 HILP를 반환할 때** 하나입니다. 이때 워크플로는 `needs-human`과 함께 `question`, `warning`, `precheckPath`를 돌려주고 끝납니다. 사람은 `precheck.html`로 무엇 때문에 멈췄는지 확인하고, 답을 보태 `/ih`를 다시 실행합니다.

## 6. 산출물 (Evidence)

| 산출물 | 경로 | 만드는 단계 |
|---|---|---|
| 구현 전 점검 HTML | `docs/evidence/youngeun/{TASK-번호-작업명}/precheck.html` | prepare (HILP일 때도) |
| 구현 결과 보고 HTML | `docs/evidence/youngeun/{TASK-번호-작업명}/report.html` | verify (PASS일 때만) |

- 작업 폴더는 첫 prepare가 `TASK-001-bugfix` 같은 형식으로 정하고, 이후 라운드와 다른 단계가 **같은 폴더**를 씁니다.
- 두 HTML은 **팀 공통 템플릿**(`docs/templates/`)을 복사해 `{{...}}`를 채워 만듭니다. 원본 템플릿은 고치지 않습니다.
- FAIL이면 report는 만들지 않습니다. 실패 내용은 `issues`로 prepare에 전달됩니다.

## 7. 설계 결정

- **서브에이전트 분리**: 점검·구현·검증을 서로 다른 대화로 나눠, 구현한 쪽이 자기 결과를 그대로 승인하지 못하게 했습니다.
- **체크리스트 3개**: prepare가 구현 전에 "끝나면 무엇을 봐야 하는가"를 정해 두면, verify가 그 기준으로 확인합니다. 구현 후에 기준이 바뀌는 것을 막습니다.
- **실패 시 prepare로 회귀**: 바로 implement로 돌아가지 않고 prepare를 거칩니다. 실패 원인을 다시 점검해 체크리스트와 방향을 바로잡은 뒤 구현하게 하려는 것입니다.
- **라운드 상한 3회**: 같은 문제로 무한히 도는 것을 막고, 도달하면 결과에 드러냅니다.
- **확인하지 못한 것은 통과가 아님**: 실행하지 못한 테스트는 "미실행"으로 적고 통과로 치지 않습니다.
- **Report는 PASS일 때만**: 보고서가 통과 사실의 증거가 되도록 합니다.
