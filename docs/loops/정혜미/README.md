# 정혜미의 Loop 설계: "전후 사진 비교" 리팩토링 Loop

battery 프로그램의 **코드 구조를 정리할 때** 쓰는 Loop입니다. Dynamic Workflow로 만들며, 이 문서에는 **설계 설명만** 적습니다. (Loop 코드는 이 문서에 없습니다.)

> 이 문서는 첫 실행(REFACTOR-001)에서 배운 것을 반영해 한 번 고쳤습니다. 무엇이 바뀌었는지는 12장에 있습니다.

## 1. 한 줄 설명

리팩토링 전에 **"전 사진"을 찍어 두고**, 코드를 정리한 뒤 **같은 방법으로 "후 사진"을 찍어 한 글자도 다르지 않은지** 비교해서, 동작이 그대로라는 것을 증거로 남기는 Loop입니다. 그리고 시작하기 전에 **그 계획이 실제로 가능한지, 이득이 있는지**도 먼저 따져 봅니다.

## 2. 왜 이런 Loop인가

리팩토링은 **겉으로 보이는 동작이 하나도 바뀌지 않아야** 성공입니다. 그런데 "테스트가 통과했다"만으로는 부족합니다. 테스트가 확인하지 않는 곳이 바뀌어도 초록불이 켜지기 때문입니다. 또 **하면 안 되는 리팩토링**(불가능하거나 이득이 없는 것)을 걸러내지 않으면 구현과 검증에 시간만 씁니다.
그래서 이 Loop는 안전망을 네 겹으로 칩니다.

| 겹 | 언제 | 무엇으로 | 잡아내는 것 |
|---|---|---|---|
| 0 | 구현 전 | **실현성 점검 + 효과 측정** | 조건끼리 충돌해서 구현이 불가능한 계획, 이득이 사실상 없는 리팩토링 |
| 1 | 구현 후 | 빌드와 단위 테스트, E2E 전체 | 원래 있던 규칙과 화면 흐름이 깨진 것 |
| 2 | 구현 후 | **전후 계산 사진 비교** | 테스트가 직접 확인하지 않는 계산 결과의 미세한 변화 |
| 3 | 구현 후 | **변경 범위 대조** | 승인받은 범위 밖을 건드렸거나, 리팩토링에 기능·수정이 섞인 것 |

## 3. 범위

- **다루는 일:** 동작을 바꾸지 않는 내부 정리. 예: 반복 조회를 하나로 줄이기, 긴 메서드 나누기, 복잡한 자료형 정리, 이름 바꾸기, 자료구조 교체(목록 탐색 → 조회용 표)
- **다루지 않는 일:** 기능 추가, 버그 수정, 결과가 달라지는 성능 개선. 각각 검증 방법이 다르기 때문에 따로 둡니다.
- **알려진 결함은 그대로 둡니다.** 지금 E2E에는 일부러 "실패해야 통과"로 표시한 알려진 결함 3개(E2E-013b, 033, 035)가 있습니다. 리팩토링 뒤에도 이 셋은 **여전히 같은 모양으로 실패해야** 합니다. 하나라도 갑자기 통과하면 동작이 바뀐 것이므로 멈추고 사람에게 알립니다. (고치는 일은 버그 수정 Loop의 몫입니다.)

## 4. 흐름

```
 요청 (무엇을 어떻게 정리할지)
  ▼
[기준선]       초록 상태인지 확인 + "전 사진" 촬영
  ▼
[사전 검토]    Node 4개가 따로 점검 (A 문서 규칙 / B 영향 범위 / C 보존 범위·계획 / H 효과 측정)
  ▼
[실현성 점검]  Node 2개가 "이 계획이 정말 가능한가"를 반증해 봄 (G1 언어 제약 / G2 저장·호환)
  ▼
[계획]         결과를 합쳐 계획과 경고를 만듦 ──► precheck.html
  ▼
 ★ 사람 확인 ①   경고(불가능·이득 없음)를 먼저 보고 승인 / 수정 / 중단
  ▼
[구현]         승인된 파일 목록 안에서만 코드 정리
  │               └─ 코드를 하나도 못 바꾸고 멈추면 ─► 검증 없이 바로 사람에게
  ▼
[검증]         Node 3개: 빌드·테스트 / E2E 전체 / 사진 비교·범위 대조 ──► report.html
  ├─ 계획과 다르게 한 것이 있음 ─► 바로 사람에게 (승인이 필요한 문제라 반복해도 소용없음)
  ├─ 같은 실패가 두 번 연속 ─► 바로 사람에게
  ├─ 그 밖의 실패 ─► [피드백] ─► 구현으로 돌아감 (최대 3번)
  ▼
 ★ 사람 확인 ②   결과 승인 / 수정 요청
  ▼
 완료  (commit·PR은 사람이 직접)
```

모든 Node는 Subagent라서 **새 대화로 시작**합니다. 앞 단계의 판단에 끌려가지 않고 각자 증거만 보고 결론을 냅니다.

## 5. 단계별로 하는 일

### 기준선 (구현 전)
- **초록 상태 확인:** 빌드, 단위 테스트, E2E 전체가 통과하는지 먼저 봅니다. 이미 깨져 있으면 리팩토링을 시작하지 않고 사람에게 알립니다. (깨진 상태에서 시작하면 나중에 누가 깨뜨렸는지 알 수 없습니다.)
- **전 사진 촬영:** 개발 앱(8080)이 아니라 **별도 포트·메모리 DB로 띄운 앱**에서, 대표 입력 묶음으로 경로 계산 결과를 받아 파일로 저장합니다. 모든 입력의 세 경로안 전체(소요 일수, 비용, 배별 일정, 일별 생산·재고)가 대상입니다.
  - 대표 입력: 기본 수량, 한 나라만 주문, 재고 상한 초과, 배 1척, 총 수량 상·하한 부근 등 규칙이 다르게 작동하는 경우

### 사전 검토 (Node 4개)

| Node | 하는 일 |
|---|---|
| A. 문서 규칙 | 요청한 정리가 `PRD.md`, `INTENT.md`의 "반드시 지킨다"와 어긋나는지 봅니다. (예: `Planner`에 DB·화면 의존을 끌어들이면 안 됨, 검산을 지우면 안 됨) |
| B. 영향 범위와 안전망 구멍 | 바뀌는 파일과 그것을 부르는 곳을 찾고, **바뀌는 코드를 지켜 주는 테스트가 있는지** 확인합니다. 없으면 정리 전에 테스트를 먼저 보강하자고 제안합니다. |
| C. 바꾸면 안 되는 것과 계획 초안 | 바뀌면 안 되는 것(API 응답 모양, 화면 문구, DB 컬럼, **이미 저장된 계획 JSON을 읽는 방식**)을 정하고, 허용할 파일 목록과 단계별 계획을 씁니다. 한 번에 하나의 정리만 합니다. |
| **H. 효과 측정** | 요청의 동기(성능·가독성·중복 제거 등)를 한 문장으로 적고, **지금 그것이 얼마나 문제인지 숫자로 잽니다.** 성능이 동기라면 같은 코드를 수백만 번 호출해 걸린 시간을 재고, 실제로 얼마나 자주 불리는지도 적습니다. 이득이 사실상 없으면 접는 것을 권고합니다. 측정에 쓰는 파일은 저장소 밖 임시 폴더에만 둡니다. |

### 실현성 점검 (Node 2개)
계획의 모든 조건("바꾸면 안 되는 것" + "허용 파일 안에서만" + "요청한 방식")을 **동시에 만족하는 구현이 정말 존재하는지** 서로 다른 관점에서 **반증을 시도**합니다. 확신이 없으면 "불가능"으로 표시해서 사람이 보게 합니다.

| Node | 관점 |
|---|---|
| G1. 언어·타입 제약 | Java 규칙과 충돌하는가. (예: `record`는 인스턴스 필드를 가질 수 없다) |
| G2. 저장·직렬화·호환 | JSON 모양, 이미 저장된 데이터, `equals`/`hashCode`, 기존 호출부와 충돌하는가 |

### 계획과 경고
- A·B·C·H·G의 결과를 합쳐 계획을 만들고 `precheck.html`을 씁니다.
- **경고(flags)** 는 에이전트의 판단에 맡기지 않고 **스크립트가 직접** 만듭니다. 실현 불가능 의심, 이득 없음, 이득 확인 못함이 있으면 에이전트가 "진행 가능"이라고 써도 권고를 "사람에게 물을 것이 남음" 또는 "접는 것 고려"로 내립니다.

### 구현
- ①에서 승인된 **파일 목록 안에서만** 고칩니다. 정리 중 버그나 개선할 점이 보여도 고치지 않고 report에 메모로만 남깁니다.
- 계획대로 할 수 없으면 **임의로 다른 방법을 고르지 않고** 이유를 적고 멈춥니다. 승인받지 않은 대안을 사용자의 말을 근거로 정당화하지 않습니다.

### 검증 (Node 3개)

| Node | 하는 일 |
|---|---|
| D. 빌드·단위 테스트 | 빌드와 `PlannerTest`, `OrderFlowTests` 등 단위 테스트를 실행합니다. |
| E. E2E 전체 회귀 | 별도 포트·메모리 DB에서 E2E 전체를 실행합니다. 알려진 결함 3개가 **예상대로 실패한 채** 그대로인지도 따로 셉니다. |
| F. 사진 비교와 범위 대조 | ① 같은 입력으로 "후 사진"을 찍어 "전 사진"과 **글자 단위로** 비교합니다. ② 바뀐 파일이 승인된 목록과 같은지, 화면 문구·API 응답·DB 구조가 바뀌지 않았는지 대조합니다. ③ 결과를 정리해 report를 씁니다. |

D·E·F는 빌드가 서로 충돌하지 않도록 **순서대로** 돌립니다.

## 6. 사람이 확인하는 곳 (HITL)

- **① 구현 전:** 경고와 점검 결과, 허용 파일 목록, 계획을 보고 승인 / 수정 / 중단. **경고가 있으면 그것부터 봅니다.** 승인 전에는 코드를 바꾸지 않습니다.
- **② 구현 후:** 비교 결과와 변경 내용을 보고 승인 / 수정 요청.
- 사람 확인은 워크플로 안에서 기다릴 수 없어서, **두 번에 나눠 실행**합니다. 사전 검토까지(`prepare`)를 실행하고 사람이 확인한 뒤, 승인된 계획으로 구현부터 끝까지(`execute`)를 실행합니다.

## 7. 끝나는 조건

- **정상 종료:** 빌드·테스트·E2E가 통과하고, 사진 비교가 같고, 범위 밖 변경이 없고, 알려진 결함 3개가 그대로이며, 계획과 다르게 한 것이 없고, 사람이 ②에서 승인
- **중단:** 기준선이 이미 깨져 있거나 사람이 ①에서 중단을 선택
- **사람에게 넘김 (이유를 report에 적고 멈춥니다):**

| 이유 | 언제 |
|---|---|
| 구현이 막힘 | 코드를 하나도 바꾸지 못하고 멈춤. 같은 입력으로 다시 해도 같은 결과라 **검증도 돌리지 않고** 바로 넘깁니다. |
| 승인이 필요한 변경 | 계획과 다르게 구현한 부분이 있음. 사람이 승인해야 풀리는 문제라 반복하지 않고 바로 넘깁니다(검증 결과는 함께 보여 줍니다). |
| 같은 실패 반복 | 두 번 연속 같은 항목이 같은 이유로 실패. 더 고쳐도 같은 결과입니다. |
| 최대 횟수 | 다른 실패를 3번 반복해도 통과하지 못함 |

## 8. 산출물

```
docs/evidence/정혜미/{작업번호+작업명}/     예: REFACTOR-001-master-days
├─ precheck.html   구현 전 점검 (요청 요약, 문서 규칙, 영향 범위, 안전망 구멍, 실현 가능성, 이득 측정, 계획과 허용 파일 목록)
├─ report.html     결과 요약 (구현 요약, 바뀐 파일, 테스트 결과, 사진 비교 결과, 반복 횟수, 멈춘 이유, 남은 문제)
└─ snapshot/       전·후 계산 사진 파일 (비교의 원본 증거)
```

`precheck.html`과 `report.html`은 `docs/templates/`의 공용 템플릿을 씁니다.

## 9. 지키는 규칙

- 코드 수정은 ①에서 승인된 뒤에만, 승인된 파일 목록 안에서만 합니다.
- 개발 앱(8080)과 개발 DB는 건드리지 않습니다. 검증은 별도 포트·메모리 DB에서만 합니다.
- 마스터를 바꾸는 사진·테스트는 끝나면 반드시 원래 값으로 되돌립니다.
- commit, push, PR은 자동으로 하지 않습니다. 사람이 요청할 때만 합니다.
- **통과하지 않았는데 통과했다고 쓰지 않습니다.** 확인하지 못한 것은 "확인하지 못함"이라고 적습니다.
- 알려진 결함 3개를 "통과"로 섞어 세지 않고 따로 적습니다.
- **승인받지 않은 대안을 임의로 구현하지 않습니다.** 계획을 이룰 수 없으면 멈추고 사람에게 알립니다.
- 같은 실패를 반복해서 시간을 쓰지 않습니다. 반복하면 멈춥니다.
- 파일 경로는 저장소 루트 기준 상대 경로나 `C:/work/...` 형식만 씁니다. (`/c/...`처럼 드라이브 없이 쓰면 저장소 밖에 폴더가 생깁니다.)

## 10. 이번에 넣지 않은 것

Lint·Formatter, 보안·성능 검증, 화면 스크린샷 비교, 자동 commit·PR·배포, 기능 추가·버그 수정용 Loop. 필요하면 Node를 추가해 확장합니다.

## 11. 테스트 계획과 진행 상황

작은 요청 하나로 Loop를 돌려 봅니다.

> `Master.days()`가 항로 목록을 매번 처음부터 찾는데, 조회용 표로 바꿔 같은 결과를 더 간단히 얻게 한다.

| 확인할 것 | 상태 |
|---|---|
| 1. `precheck.html`, `report.html`, `snapshot/`이 증거 폴더에 만들어지는지 | **확인함** (REFACTOR-001에서 모두 만들어짐) |
| 2. 사진 비교가 "같음"으로 나오고, 알려진 결함 3개가 그대로인지 | **확인함** (13개 모두 동일, 알려진 결함 3개 그대로) |
| 3. (일부러 틀려 보기) 계산 결과가 미세하게 달라지는 변경(예: 반올림 방식 변경)을 넣어 F가 **실패로 잡아내는지** | **아직 하지 않음** |
| 4. (새 안전장치) 12장의 점검이 같은 상황에서 실제로 경고를 내는지 | **아직 하지 않음** (다음 `prepare`에서 확인) |

- 이 테스트로 바뀐 코드는 **commit하지 않습니다.**

## 12. 첫 실행에서 배운 것 (REFACTOR-001)

**무슨 일이 있었나:** `Master.days()`를 조회용 표로 바꾸려 했지만, `Master`가 `record`라서 "저장 형식·JSON·생성자를 그대로 두면서 인스턴스 안에 조회표를 두기"가 **언어 규칙상 불가능**했습니다. 구현은 두 번 멈췄고, 세 번째에 승인받지 않은 정적 캐시로 우회했습니다. 모든 검증은 통과했지만, 측정해 보니 호출당 약 0.2마이크로초로 **이득이 없어서** 이 리팩토링은 접었습니다. 같은 이유로 세 번 반복하는 동안 에이전트 13개(약 57만 토큰)를 썼습니다.

**고친 것:**

| 문제 | 고친 방법 |
|---|---|
| 불가능한 계획을 사람이 승인해 버림 | 구현 전에 **실현성 점검(G1·G2)** 으로 조건들의 충돌을 반증해 봄 |
| 이득이 없는 리팩토링을 시작함 | 구현 전에 **효과 측정(H)** 으로 동기를 숫자로 확인 |
| 막힌 구현을 3번 반복하고 매번 검증까지 돌림 | 구현이 막히면 즉시 중단, 같은 실패 두 번이면 중단, 승인이 필요한 변경이면 즉시 중단 |
| 에이전트가 승인받지 않은 대안을 사용자의 말로 정당화함 | 구현은 계획대로 못 하면 멈추고, 승인받지 않은 대안은 임의로 고르지 않는다는 규칙 추가 |
| E2E 결과 파일이 저장소 밖(`C:\c`)에 만들어짐 | 경로 지시를 상대 경로로 고침 |
