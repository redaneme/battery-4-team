# basic-guide

현재 프로젝트의 **실제 소스코드**를 읽고, 개발 지식이 없는 사람이 단계별로 이해할 수 있는
**3개 탭의 인터랙티브 HTML 웹앱**을 `./docs/basic_guide.html`에 만든다(이미 있으면 갱신한다).

## 원칙

- **코드가 근거다.** 추측하지 않는다. 설명·숫자·규칙은 모두 소스에서 확인한 것만 쓴다. 확인하지 못한 부분은 "확인 필요"로 표시한다.
- **개발 용어 금지.** 클래스·API·DB·엔티티·트랜잭션 같은 말을 본문에 쓰지 않는다. 업무 언어(주문, 공장, 상태, 비용, 일정 등)로 바꿔 쓴다. 불가피한 낱말은 쉬운 풀이를 붙인다.
- **한 단계 = 한 가지 질문.** 단계마다 "이걸 알면 다음으로 간다"는 하나의 이해 목표만 둔다.
- 독자는 코드를 처음 보고, 이해에 많은 에너지를 쓸 수 없으며, 나중에 코드 리뷰를 하게 될 사람이다. 짧고 시각적으로 쓴다.

## 절차

### 1. 프로젝트 파악 (읽기만)

다음 순서로 필요한 만큼만 읽는다. 모두 읽지 않아도 되지만, 안내서에 쓸 내용은 반드시 읽고 쓴다.

1. 구조 파악: 파일 목록, 빌드 설정, 설정 파일, README가 있으면 README.
2. 업무 규칙이 있는 곳 우선: 서비스/업무 로직, 계산·시뮬레이션 코드, 상태 변화 규칙, 입력 검증.
3. 기준 데이터: 초기값·기본 설정·마스터 데이터.
4. 테스트: 기대 동작이 코드로 적혀 있어 규칙 확인에 좋다.
5. 화면: 사용자가 실제로 하는 일(메뉴·입력·버튼) 확인.

읽으면서 아래를 업무 언어로 메모한다.

- 이 서비스는 **누가 무엇을 하려고** 쓰는가
- 사용자가 거치는 **업무 흐름**(입력 → 확인 → 확정 → 진행)
- **핵심 규칙과 숫자**(제한값, 기본값, 계산 방식, 상태 전이 순서, 거부되는 경우)
- **눈에 띄는 동작**(삭제되는 것, 막히는 것, 동시 변경 처리 등 리뷰 때 알아야 할 점)

### 2. 3단계 구성 정하기

기본 틀은 아래와 같다. 프로젝트 성격에 맞게 제목과 내용을 바꿔도 되지만 **"전체 그림 → 핵심 계산/규칙 → 진행·상태"** 의 흐름은 유지한다.

| 탭 | 이해 목표 | 포함할 것 | 인터랙티브 예시 |
|---|---|---|---|
| ① 무엇을 하는 서비스인가 | 누가 무엇을 위해 쓰는지 | 한 줄 요약, 업무 흐름 4~5단계, 알아둘 낱말 3~5개 | 핵심 대상(나라·부서·상품 등)을 눌러 상세 정보를 보는 지도/카드 |
| ② 핵심 규칙은 어떻게 동작하나 | 입력이 결과가 되는 과정 | 규칙을 쉬운 말로 3~5줄, 기준값 | 입력값을 바꾸면 결과가 즉시 다시 계산되는 체험 |
| ③ 진행과 상태는 어떻게 관리되나 | 상태 변화와 예외 상황 | 상태 순서, 허용/금지되는 변화, 이력, 리뷰 때 알아둘 점 | 버튼으로 상태를 바꿔 보고 거부되는 경우를 직접 확인 |

프로젝트에 상태 관리가 없다면 ③은 "자주 마주치는 예외·검증 규칙" 등 그 프로젝트의 세 번째 핵심으로 대체한다.

### 3. HTML 만들기

`./docs/basic_guide.html`이 이미 있으면 먼저 읽고, 구조·스타일을 유지한 채 **코드와 달라진 내용만** 고친다. 없으면 새로 만든다. `docs` 폴더가 없으면 만든다.

**기술 요건**

- **파일 하나로 완결**: HTML/CSS/JS를 한 파일에 넣는다. 외부 라이브러리·CDN·이미지 요청 없이 브라우저에서 더블클릭으로 열려야 한다. `lang="ko"`, `meta viewport`를 넣는다.
- **탭**: `role="tablist"` / `role="tab"` / `role="tabpanel"`, `aria-selected`, `aria-controls`를 쓰고, 좌우 화살표 키로 이동되며, 각 탭 끝에 "다음 단계" 버튼을 둔다. 탭을 바꾸면 화면 맨 위로 올린다.
- **인터랙션**: 탭마다 최소 1개의 직접 해보는 기능을 넣는다(위 표 참고). 입력 검증 실패 시 이유를 화면에 보여 준다. 실제 코드의 검증 규칙을 따른다.
- **접근성/디자인**: 색을 CSS 변수로 정의하고 `prefers-color-scheme: dark`에 대응한다. 키보드 포커스가 보이게 한다. 모바일 폭에서도 가로 스크롤이 없어야 한다.
- **안전**: 사용자 입력은 `textContent`로 넣고 `innerHTML`로 넣지 않는다.

**내용 요건**

- 인터랙티브 계산은 **실제 코드의 규칙을 그대로 옮긴다**. 전부 옮기기 어려우면 일부만 옮기고, 화면에 "학습용 계산이며 ○○ 안만 다룬다"고 **명시**한다.
- 기본값·제한값은 코드에서 읽은 값을 쓰고, 화면 하단에 "코드의 초기값 기준이며 운영 중 바뀔 수 있다"는 취지를 적는다.
- 리뷰 때 알아야 할 **눈에 띄는 동작**(예: 취소하면 기록이 삭제됨)은 ③ 탭에 "알아둘 점"으로 넣는다.

### 4. 검증

- 스크립트를 파일로 떼어 `node --check`로 문법을 확인한다.
- 가능하면 계산 로직을 같은 입력으로 코드의 기대값(테스트에 있는 사례 등)과 비교한다. 비교하지 못했으면 보고에 그렇게 적는다.
- 개발 용어가 본문에 남아 있지 않은지 훑는다.
- 브라우저에서 직접 열어 확인하지 못했다면 **확인하지 못했다고 사실대로 말한다.**

### 5. 보고

사용자에게 아래만 짧게 알린다.

- 파일 경로(`./docs/basic_guide.html`)와 새로 만들었는지 갱신했는지
- 3개 탭의 제목과 각 탭의 체험 기능 한 줄씩
- 단순화한 부분, 확인하지 못한 부분, 코드에서 발견한 리뷰 포인트
- 커밋은 사용자가 요청할 때만 한다.

## 하지 말 것

- 소스코드를 수정하지 않는다(읽기 전용 분석 + 안내서 파일만 쓴다).
- 읽지 않은 코드에 대해 설명을 쓰지 않는다.
- 외부 서비스로 파일을 올리거나 게시하지 않는다.
- 본문에 클래스명·메서드명·파일명을 나열하지 않는다. 필요하면 화면 하단 "참고: 근거가 된 파일" 한 줄 접이식으로만 둔다.
