# battery-code-html

이 프로젝트 **전용** Skill이다. battery 프로젝트의 소스를 읽고, 처음 보는 팀원이 구조와 핵심 로직을 이해할 수 있는 **HTML 파일 한 장**을 만든다.

## 결과물

- 파일: `docs/understand/허주/battery-code-guide.html`
- 외부 라이브러리·CDN·이미지 파일 없이 **파일 하나로 완결**한다. 인터넷이 없어도 열려야 한다. 다이어그램은 인라인 SVG나 CSS로 그린다.
- 밝은 화면/어두운 화면 모두 읽기 좋게 한다(`prefers-color-scheme`). 모바일 폭에서도 가로 스크롤이 생기지 않게 한다.
- 계산기·입력 폼 같은 동적 기능은 넣지 않는다. 플래너 설명은 **정적 단계별 풀이**로 한다.

## 진행 순서

### 1. 코드를 직접 읽는다 (기억에 의존하지 않는다)

최소한 아래를 읽고 시작한다. 이미 알고 있다고 생각해도 현재 코드가 바뀌었을 수 있으니 다시 확인한다.

- 빌드·설정: `build.gradle.kts`, `src/main/resources/application.properties`
- 진입·설정: `DemoApplication`, `config/` (`WebConfig`, `LoginInterceptor`, `DataInitializer`, `JpaConfig`)
- 화면·API: `controller/AppController`, `templates/*.html`, `static/js/*.js`
- 업무 로직: `service/BatteryService`, `service/BusinessException`
- 계산 핵심: `simulation/Planner`, `Master`, `Plan`, `StoredPlan`
- 데이터: `entity/*`, `repository/*`
- 테스트: `PlannerTest`, `OrderFlowTests`

### 2. 실제 실행 결과로 풀이용 수치를 만든다

설명에 쓰는 일수·비용·적재량은 **손으로 계산하지 않고 실제 코드 실행 결과**를 쓴다.

```
./gradlew test --tests "com.example.demo.simulation.PlannerTest" --rerun-tasks
```

- `PlannerTest.defaultOrderSummary`가 기본 주문(중국·일본·베트남·인도네시아 각 3,000K, 배 3척)의 3가지 경로를 출력한다.
- 콘솔에서는 한글이 깨진다. 결과는 `build/test-results/test/TEST-com.example.demo.simulation.PlannerTest.xml`의 `system-out`을 UTF-8로 읽는다.
- 단순 사례(베트남 2,000K 단독 등)는 `PlannerTest`의 단위 테스트 주석과 단언에서 확인한다.

### 3. HTML을 아래 구성으로 만든다

1. **한눈에 보기** — 시스템이 무엇을 하는지 한 문단, 한국 허브와 4개 공장과 배를 보여 주는 그림, 용어(K, 셀, 재고 상한, 왕복)
2. **아키텍처** — 화면(Thymeleaf+JS) → `AppController` → `BatteryService` → `Planner`·리포지토리 → H2 계층도
3. **파일 지도** — 패키지별 파일이 맡은 역할 표
4. **주문 흐름** — 시뮬레이션 → 확정(서버 재계산, 마스터 버전 검증) → 상태 전이, 낙관적 락
5. **플래너 알고리즘 (핵심)** — 규칙 요약, 경로 3가지(COST/FAST/NEAR) 차이, 단계별 정적 풀이
6. **데이터 모델** — 엔티티 관계, 주문 상태 전이도, 스냅샷(`planJson`) 개념
7. **마스터 기본값과 설명 대조** — 코드 초기값 표, 설명과 다른 점
8. **읽는 순서 가이드** — 어떤 파일부터 어떤 순서로 읽으면 좋은지, 어떤 테스트가 무엇을 보장하는지
9. **팀 합의 필요 항목** — **시스템 요구사항(PRD)에 한정한다.** 사용자가 알려준 시스템 설명에 값이나 규칙이 없거나 코드와 다른 항목만 모아 *PRD의 내용 / 현재 코드(근거 `파일:줄`) / 합의할 내용*으로 적는다. 산출물 형식(폴더 구조, Skill 형태, HTML 범위 등)과 Git 규칙(브랜치명, 커밋 메시지, 머지 방식 등)은 이 섹션에 넣지 않는다.

### 4. 반드시 지킬 원칙

- **근거 표기**: 모든 설명에 근거 파일과 줄 번호를 `Planner.java:295` 형식으로 붙인다.
- **확인과 추측 구분**: 코드로 확인한 내용과 추정한 내용을 눈에 띄게 구분해 표시한다. 추정은 "추정" 배지로 표시한다.
- **설명과 코드의 차이를 숨기지 않는다**: 사용자가 알려준 도메인 설명과 코드가 다르면 그대로 적는다. 현재 알려진 차이는 다음과 같다.
  - 공장운영비는 국가별 비용인데 "추가 개발 필요"로 되어 있고, 현재 코드에는 없다. 총비용은 생산비+운항비뿐이다.
  - 생산원가는 셀당 500~1,000원 범위라고 했으나, 코드 초기값 인도네시아는 450원이다.
  - 설명의 일일 최대 생산량 예시는 0.1K/일이고, 코드 초기값은 200~800K/일이다(예시값이므로 오류로 단정하지 않는다).
- **실습용 시스템**: 데이터가 완전하지 않을 수 있는 실습용 시스템임을 한 줄로 밝힌다.
- **수량 단위**: 수량은 K(1,000개) 단위, 금액은 억 원 단위로 표기하고 단위를 항상 붙인다.
- **코드의 가정을 숨기지 않는다**: 사용자가 알려준 시스템 설명에 없는데 코드가 임시 값이나 규칙으로 구현해 둔 것은 9번 섹션에 합의 필요 항목으로 적는다. 코드 열의 값은 확인한 사실만 쓰고, 합의할 내용은 제안임을 밝힌다.

### 5. 만든 뒤에 검증한다

- 본문에 쓴 모든 수치가 2단계 실행 결과와 일치하는지 대조한다.
- 인용한 파일 경로와 줄 번호가 실제 코드와 맞는지 확인한다(`Grep`으로 해당 줄 확인).
- 외부 URL(`http`)이나 외부 파일 참조가 남아 있지 않은지 확인한다.
- 브라우저에서 열어 깨지는 곳이 없는지, 밝은/어두운 화면에서 글자가 읽히는지 본다.
- 검증하지 못한 부분이 있으면 사용자에게 그대로 알린다.

### 6. 하지 않는 것

- 소스 코드, 설정, 마스터 데이터를 수정하지 않는다. 이 Skill은 읽기와 HTML 생성만 한다.
- 커밋·푸시·PR은 하지 않는다. 그 단계는 사용자가 요청할 때 한다.
